## 2. 결정 사항 (2026-10-02)

1. **경품은 품목별 카테고리로 묶는다.** 사장님이 카테고리 안에서 경품 목록을 직접 등록·조회·수정·삭제(CRUD)한다.
2. **기본 카테고리 7종을 제공한다** (3장). 어떤 카테고리를 쓸지는 사장님이 고른다.
3. **경품 카드 이미지는 카테고리별로 우리가 직접 생성한 이미지를 쓴다.** 실제 카드·경품 사진은 쓰지 않는다 (3.2).
4. **오리파 방식 수량 제한.** 경품마다 수량을 정해 두고, 그 수량 안에서만 나온다.
5. **고른 1장만 차감.** 팩에는 5장이 나오지만 사용자가 최종 선택한 1장만 수량에서 1 차감된다. 고르지 않은 4장은 차감되지 않는다.
6. **품절 경품은 제외.** 어떤 경품의 남은 수량이 0이 되면 이후 팩에는 나오지 않고, 남은 경품만으로 5장이 결정된다.
7. **남은 경품 종류가 5종 미만이면 중복을 허용한다** (4장).
8. **확률 입력 없음.** 어드민에서 확률을 설정하지 않는다.
9. **게임은 매장 기기 1대, 어드민은 사장님 기기에서 사용한다.**

## 3. 카테고리

### 3.1 기본 카테고리

| 순서 | 카테고리 | ID (제안) | 현재 코드 대응 |
|---|---|---|---|
| 1 | 베이커리 이용권 | `bakery` | 없음 (신규) |
| 2 | 음료 이용권 | `drink` | `cafe` (카페 음료) |
| 3 | 카드 슬리브 | `sleeve` | 없음 (신규) |
| 4 | 카드 세이버 | `saver` | 없음 (신규) |
| 5 | 부스터팩 | `booster` | `pack` (부스터팩) |
| 6 | 카드 | `card` | 없음 (신규) |
| 7 | 할인권 | `discount` | `coupon` (할인권) |

- 현재 코드(`design/lib/icons.js`, `src/data/api.ts`의 `CATEGORIES`)는 7종 모두 대응한다. 프론트 키는 `card` / `pack` / `cafe` / `sleeve` / `saver` / `bakery` / `coupon`이고, 서버 아이콘 이름 `drink`·`booster`·`discount`는 `src/data/api.ts`에서 각각 `cafe`·`pack`·`coupon`으로 바꿔 쓴다.
- `icons.js`에는 기본 카테고리에 없는 `sticker`(카드 씰)가 아직 남아 있다 (시안 갤러리 목업 데이터용).
- 카드 앞면은 카테고리를 두 곳에서 쓴다 (`design/lib/card.js`):
  - 우상단 작은 아이콘 (28px) + 일러스트 창 아래 카테고리 이름
  - 일러스트 창 (`WINDOW_BOX`) — 카테고리 일러스트(`src/card/artwork/*.webp`)를 표시
  - → 신규 카테고리 4종의 아이콘도 새로 그려 넣었다 (9장 Q4).

### 3.2 카테고리 이미지

- **카테고리마다 이미지 1장**을 직접 생성해 경품 카드의 일러스트 창에 넣는다. 같은 카테고리의 경품은 같은 이미지를 공유한다.
- 이유:
  - 실제 카드·경품(포켓몬 카드, 부스터팩 등) 사진은 **저작권 문제**가 생길 수 있다.
  - 사진은 카드 디자인과 **이질감**이 생긴다.
- 7종 모두 생성 완료 (원본 `design/concepts/`, 카드용 `src/card/artwork/`, 오리파 화면용 `src/ui/category/`). 생성 시 참고한 조건:
  - 실제 상품의 로고·캐릭터·패키지 디자인을 재현하지 않는다 (포켓몬 IP 미사용 — 명세 1장).
  - 카드 디자인 톤에 맞춘다: 아이보리·금색 팔레트, "바다 위 해돋이"(포항/호미곶) 모티프 (PROGRESS.md M0-2).
  - 등급마다 일러스트 창 배경이 달라지므로 (`card.js` `windowArt`) 배경과 어울리는지 확인 필요 — 투명 배경 여부는 생성 시 결정.
  - 크기: 일러스트 창은 카드 좌표 546×356 (가로:세로 ≈ 1.53:1). 카드 텍스처가 1.25배(788×1100)로 래스터화되므로 실제 표시 약 683×445px → **2배 여유로 약 1092×712px 이상** 권장.
- 사장님이 기본 7종 외 카테고리를 새로 추가하면 생성 이미지가 없다 → 처리 방식 미정 (9장 Q3).

## 4. 추첨 규칙

### 4.1 확정
- 추첨 대상 = 남은 수량(`remaining`)이 1 이상인 경품만.
- 사용자가 "이 상품으로 결정"을 누른 순간에만 해당 경품 `remaining`을 1 차감한다. 연출 도중 새로고침·이탈 시에는 아무것도 차감되지 않는다.
- 남은 경품 종류가 5종 미만이면 **같은 경품을 중복으로 넣어** 5장을 채운다.
  - 고른 1장만 차감하므로, 남은 수량보다 많이 노출되어도 문제없다 (예: 남은 수량 1인 경품이 2장 나와도 1장만 가져감).
  - 남은 경품이 전부 0이면 팩을 만들 수 없음 → 게임 시작 차단 + "이벤트 종료" 표시 (6.2 제안과 연결).

### 4.2 제안 (확인 필요 — 9장 Q5)
- **남은 수량 비례 추출.** 남은 경품 1개 = 추첨권 1장으로 보고, 남은 수량이 많은 경품일수록 잘 나온다. 확률을 따로 입력하지 않아도 수량이 곧 확률이 되며, 수량이 줄어들수록 자동으로 바뀐다.
- **5종 이상 남아 있으면 5장 모두 다른 경품** (기존 명세 2장 유지). 한 장 뽑을 때마다 그 경품을 후보에서 빼고 다음 장을 뽑는다.
- **5종 미만일 때 중복 채우는 방법**: 남은 종류를 1장씩 먼저 넣고, 빈자리는 남은 수량 비례로 다시 뽑는다.
- 카드 넘기는 순서는 기존대로 등급 오름차순 (명세 R9: 레어는 뒤쪽).

### 4.3 운영상 알아 둘 점
- **고등급 조기 소진.** 사용자가 5장 중 원하는 것을 고르므로, 고등급이 5장 안에 나오면 대부분 선택된다. 총 플레이 수(= 전체 수량 합)는 그대로지만, 좋은 경품은 이벤트 초반 손님에게 몰리기 쉽다 (9장 Q6).

## 5. 저장 방식 — 백엔드로 결정

- 게임은 매장 기기, 어드민은 사장님 기기로 **서로 다른 기기**다.
- 브라우저 저장소(localStorage)는 기기마다 따로라서, 사장님 기기에서 바꾼 경품·수량이 매장 기기 게임에 반영되지 않고, 매장 기기에서 차감된 수량도 사장님 기기에서 보이지 않는다.
- 따라서 **"백엔드 없이" 방향은 사용자가 다시 검토하기로 함** (2026-10-02). 검토한 선택지 — **(a) 백엔드 사용으로 결정**:

| 선택지 | 내용 | 비고 |
|---|---|---|
| (a) 백엔드 사용 | 경품·수량을 서버에 두고 두 기기가 같이 읽고 씀 | 사장님 기기에서 실시간 확인·수정 가능. 서버 운영 필요 |
| (b) 어드민을 게임 기기에서도 열기 | 사장님이 매장 기기에서 어드민 진입 | localStorage만으로 가능. "사장님 기기 사용" 결정과 다름 |
| (c) 파일로 옮기기 | 사장님 기기에서 설정 → JSON 내보내기 → 매장 기기에서 가져오기 | 실시간 수량 확인 불가, 수동 작업 |

- 구현: 백엔드(Spring Boot + SQLite)를 매장 컴퓨터에서 실행하고, 게임 기기와 사장님 기기가 가게 내부망으로 같은 서버에 접속한다. 게임 코드의 서버 접근은 `src/data/api.ts` 한 곳에 모았다.

## 8. 게임 쪽 구현 (2026-10-12 기준)

기본 실행·빌드·공개 배포는 아래 서버 연결을 쓰는 운영 모드다. `VITE_GAME_MODE=demo`로 실행·빌드하면 백엔드 없는 시연 모드(`src/data/demo.ts`)가 되며, 예시 경품과 수량은 페이지 메모리에만 저장하고 재진입 시 초기화한다.

- 서버 접근은 `src/data/api.ts` 한 곳에 있다. 백엔드가 서빙한 페이지는 같은 서버의 `/api/v1`(TV·폰에서 노트북 주소로 열어도 동작), GitHub Pages·개발 서버·테스트는 `http://localhost:8080/api/v1`.
- 게임은 손님용 API만 쓴다. 백엔드의 어드민 API(`/api/v1/admin/**`)는 로그인이 필요하다.
- `fetchShop()`: 첫 번째 활성 팩(`GET /packs`)과 그 팩의 경품 목록(`GET /packs/{id}/prizes`)을 받아 오리파 화면의 남은 수량(전체·최고등급·카테고리별)을 만든다. 경품마다 서버의 `icon`이 카테고리가 된다. 카드 텍스처도 이 목록으로 미리 준비한다.
- `drawCards()`: 팩을 고르면 추첨은 서버(`POST /packs/{id}/draw`)가 하고, 프론트는 결과(`drawId`·카드 목록)만 받는다. 이때는 차감하지 않는다.
- `confirmPrize()`: "이 상품으로 결정" 시 `POST /draws/{id}/confirm`으로 고른 1장만 차감한다. 당첨 기록은 서버가 남긴다.
- 남은 수량이 모두 0이면 오리파 화면에 품절을 표시하고 팩을 열 수 없다.
- 서버 연결 실패·오류 시 인트로에 안내를 띄우고, 터치하면 처음부터 다시 시작한다.
- 같은 경품 카드가 한 팩에 여러 장 나올 수 있다 (서버가 복원 추출).

- **Q1. 저장 방식 / 백엔드 여부** — ✅ (a) 백엔드 사용. 구현 완료 (5장).
- **Q2. 쿠폰·14일 방문 흐름** — ✅ 2026-10-12 결정: 매장 전용으로 쿠폰·방문 기한·매장 정보 없이 선택 상품과 메뉴 복귀 버튼만 표시한다. 목업 쿠폰 생성 로직도 제거했다.
- **Q3. 카테고리 관리 범위** — 백엔드는 팩 단위로 경품을 묶고 경품마다 종류 아이콘을 고른다(어드민의 "기본 팩 7개 한 번에 만들기"). 게임은 첫 번째 활성 팩 1개에 모든 경품을 섞어 쓴다. 생성 이미지가 없는 새 아이콘의 표시 방법은 아직 정하지 않음. 원래 질문: 사장님이 기본 7종 중 "고르기"만 하는지, 이름 변경·신규 추가·삭제도 하는지. 신규 추가를 허용하면 생성 이미지가 없는 카테고리의 표시 방법(기본 이미지 등)이 필요. 경품이 남아 있는 카테고리 삭제 시 처리도 필요.
- **Q4. 카드 우상단 아이콘** — ✅ 신규 4종 아이콘을 새로 그림.
- **Q5. 4.2 제안 규칙 확정 여부** — ✅ 남은 수량 비례 추출로 확정. 다만 5장은 한 장씩 따로 뽑는다(복원 추출) — 5종 이상 남아 있어도 같은 경품이 여러 장 나올 수 있다 (4.2의 "5장 모두 다른 경품" 제안과 다름).
- **Q6. 고등급 조기 소진 허용 여부** — 허용하지 않는다면 팩당 고등급 노출 수 제한 등 별도 규칙 필요.
- **Q7. 7.2 제안 기능 중 넣을 것.** — ✅ 수량 빠른 조정(+/−), 등급별·전체 합계, 당첨 기록·되돌리기, 전체 초기화를 구현. PIN 잠금은 없음(가게 내부망 전제). 백업은 안내만 있음.
- **Q8. 1인 1회 제한** — 구현하지 않음(자유 플레이). 원래 질문: 기기 1대를 여러 손님이 쓰므로 기기가 사람을 구분할 수 없다. 자유롭게 플레이할지, 직원이 매번 게임을 열어 주는 방식이 필요한지.
- **Q9. 기본 경품 데이터** — 각 카테고리에 처음 들어갈 경품·등급·수량. 사장님이 어드민에서 직접 입력.
